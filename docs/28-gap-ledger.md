| **A7** | **A revoked token still authenticates** | **fixed** | **Landed 2026-10-20.** `aroute keys revoke --token-file <path>` writes the token's **session id** into a `revoked_tokens` table; both `/v1` and `/ui` consult it. The table lives in the **credential store's own sqlite file** - not a separate redb file, because redb takes an exclusive `flock` and the running proxy holds its handle open, which would make the operator's revoke command fail for exactly as long as the proxy was up. **The whole session dies, not one half**: a minted token is a pair, and the refresh half is itself a valid bearer credential, so revoking only the access half would have left a 30-day token live. The table is opened only when the store FILE is present (so the revocation path never creates a file the credential store did not already create), and it is opened even when the store cannot be decrypted, because the list needs no master. Measured cost: **p95 12.3 us** for the lookup, against a 1 ms budget. `docs/31` Phase 2 | The operator's lever, now that it exists: `aroute keys revoke --token-file <path>` on the VPS, then the token is dead on both surfaces immediately. The master rotation is still the blunt instrument for a whole-store compromise. **A revoked token's own expiry is unchanged** — only the access half is revoked, and the refresh half keeps working until it expires on its own.
| **A8** | **The panel's gate resolves its state at boot, so a gate armed or broken *after* boot is not seen** | **fixed** | **Landed 2026-10-20.** The panel's gate is resolved **per request** by `webui/livegate.rs`, so arming the gate with `aroute keys arm-gate` while the proxy runs turns the panel's gate on, and breaking the master turns it `Broken`. **The master is re-derived only when the gate row's CIPHERTEXT changes** - a cheap sqlite point read - because a per-request re-resolve would spend argon2id's **19 MiB and ~40 ms** on every request. The file's mtime is deliberately not the signal: the revocation table lives in the same sqlite file, so every `aroute keys revoke` would change it and force a re-derivation of a gate that had not changed. **The env master is the server's own resolved one** (`built.config.http_master_key`), read through the server's decoder, so the panel and `/v1` never disagree about which master is in force; the env precedence is the server's: the store's gate row first, the env master second. A store that cannot be read falls back to the env master, and only answers `Broken` when no master can open the row - `Broken` means exactly one thing, and `Unarmed` (which permits writes) is never a fallback. **Scope: the env master is captured at boot.** An environment variable cannot change under a running process, so rotating it is seen by a restart, not live. Five tests pin it, including the one only a counter can prove: an unchanged gate row must not re-derive. `docs/31` Phase 3.1 | Nothing. The gate is live per request, the three arms are preserved, and the badge and the guard read the same value. The one asymmetry left is the **env master**, which is captured at boot by construction - a rotation of `AR_HTTP_MASTER_KEY` needs a restart, which is the same rule the server itself has.

## F2. The context window and the harness surfaces (2026-10-20)

Found while adding a model to the catalog. All four rows are **closed**; they are
recorded because each one is a way the same question ("how big a prompt may I
send?") gets a different answer depending on which surface asks.

| # | item | status | what is true now |
|---|---|---|---|
| **F2.1** | **A provider with no registry ceiling fell to the 128K floor** | **closed** | The chain is: the per-model figure models.dev published → the per-provider ceiling in `providerMeta.json` → the `ModelCard::UNKNOWN_CONTEXT` floor of 128K (`crates/ar-server/src/models.rs:144`). `providerMeta.json` carries **no** `contextLength` for `kilocode` or `nvidia` — 169 of its 276 providers have none, because OmniRoute's own registry entries declare none either (75 of 272 there). So those two providers' windows came only from the models.dev overlay, and **a failed discovery refresh dropped them to 128K**: the VPS log shows `model discovery refresh failed; serving the cached catalog` (the 5-second client timeout, `DISCOVERY_WAIT_SECS`, against a 5.8 MB document). Measured: with discovery on, `ctx-kilo` reported 1,000,000; with it off, 128,000. |
| **F2.2** | **The durable place for a window is the config, not the registry** | **closed** | `providerMeta.json` is **generated** — `aroute import --from omniroute` rewrites it wholesale from OmniRoute's tree — so a hand-edit there is clobbered on the next import. The combo's own `context_length:` is the operator-owned, durable place, and it **overrides** the reduction (`crates/ar-server/src/config.rs:970-973`). Every `nvidia`/`kilocode`-routed combo now carries one: `glm-5.3` 1M, `glm-5.3-flash` 1M, `step-5-preview` 1M, `beam-free` 1M, `minimax-m3.1-flash` 1M, `nemotron-3.5-super-vl` 1M, `laguna-s-2-1` 262144, `deepseek-v4-1-flash` 1M, `browser-stack-2` 1M. Verified with discovery **off**: every window survives. |
| **F2.3** | **The two static harness model lists had drifted** | **closed** | omp resolves the catalog live (`discovery: openai-models-list`) so it needed no edit; it shows all 21. opencode's `provider.ar.models` carried **12** of 21 (9 missing, including `browser-stack-2` and every `jev`/`clef`/`weaver`/decisions model) and jcode's `[[providers.omniroute.models]]` carried **20** of 21. The lists were hand-maintained. `~/.local/bin/harness-models-sync` now renders them from the live gateway — the authority — so the window is never a guess; `--check` reports drift and changes nothing. A **wrong** window is worse than a missing entry: the harness sizes a request off it and the upstream refuses one it would have accepted. |
| **F2.4** | **jcode read a token file the token script never wrote** | **closed** | jcode resolves a profile's `env_file` against its **config home**, which is `~/.config/jcode/` — not `~/.jcode/`, where `~/.jcode/config.toml` itself lives. `scripts/gate-token.sh` wrote the token to `~/.jcode/provider-omniroute.env`, so the file jcode actually read, `~/.config/jcode/provider-omniroute.env`, kept an old `sk-omni-` Dashboard key from 13:41. The general lesson, and the thing to check first next time: **a harness can hold
a valid token and still 401, because "valid" was measured against a file the
harness does not read.** A credential check is only evidence about the surface
that made the request.
